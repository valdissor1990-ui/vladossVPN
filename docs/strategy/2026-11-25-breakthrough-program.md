# Программа прорыва vladossVPN — 2026-11-25

**Статус:** зафиксированный план, реализация волнами  
**Ветка:** `task/breakthrough-program`  
**База:** `origin/main` @ `f9e9e573`  
**Цель:** превратить клиент из «ещё одного списка серверов» в клиент, который доводит до работающего интернета и объясняет, что делать.

---

## 1. Позиционирование и главная метрика

**Обещание продукта:** личная подписка → понятный выбор сервера → работающий интернет за 15 секунд → если не работает, приложение само показывает причину и предлагает лечение.

**Главная метрика (не меняется):** ≥90% сессий с реальным интернетом через VPN за <15 с после Connect.

**Новые метрики программы:**

| Метрика | Цель | Как считаем |
|---|---|---|
| Успех после автолечения | ≥60% неудачных коннектов | сессии, где Doctor/Autopilot привели к Connected |
| Время до понятной причины | <20 с | от ошибки до показа шага диагностики |
| Использование проверки сервисов | ≥25% активных пользователей | локальные счётчики, без отправки |
| Успех импорта из конкурента | ≥95% распознанных профилей | отчёт импорта |
| Разрывы при Wi-Fi↔LTE | <2% сессий | journal |
| Crash-free sessions | ≥99,5% | Play Console / локально |
| Расход батареи в фоне | не хуже текущего | BatteryMonitor baseline |

Метрики считаются локально. Телеметрия по умолчанию отсутствует.

---

## 2. Принципы

1. **Golden path не ломаем.** Любая новая логика подключается после успешного коннекта или по явному действию пользователя.
2. **Фича-флаги.** Рискованные функции по умолчанию выключены; включаются в настройках или при первом сбое с согласием.
3. **Секреты не логируем.** UUID, ключи, URL подписок, пароли — вне логов, отчётов и экспортов.
4. **Никаких встроенных подписок и серверов.** Только пользовательские.
5. **Каждая фича — с тестами.** Чистая логика — JVM unit tests; Android-пути — instrumentation или device-тест, но без ложных заявлений.
6. **Один экран — одна задача.** Не превращать главный экран в панель управления самолётом.
7. **Обратная совместимость.** Старые настройки и профили продолжают работать.
8. **GPL-3.0-or-later и брендинг не трогаем** без отдельного решения.

## 3. Направления

### 3.1 «Доктор подключения» — диагностика с автолечением

**Сценарий:** Connect не удался или интернет пропал. Пользователь видит не «ошибка», а список шагов: что проверено, что сломано, что нажать.

**Шаги диагностики:**

| # | Шаг | Что проверяет | Лечение |
|---|---|---|---|
| 1 | Подписка | доступность URL, статус 200/304, не заглушка ли | обновить, открыть настройки |
| 2 | Профиль | `ParsedConfig.isValid()`, loopback/placeholder | переимпортировать, выбрать другой |
| 3 | DNS | резолв адреса сервера | сменить DNS, включить DoT via proxy |
| 4 | TCP | доступность host:port | сменить порт/сервер |
| 5 | TLS/Reality | handshake, SNI, fingerprint | включить фрагментацию, сменить fingerprint |
| 6 | Прокси-проба | HTTP через профиль (DeepProbe) | переключить сервер |
| 7 | TUN | создан ли интерфейс, маршруты | перезапустить core, проверить другое VPN |
| 8 | Трафик | реальный HTTP через туннель | переподключиться, сменить сервер |
| 9 | Сервисы | доступность 3–5 контрольных сервисов | показать, что именно не работает |

**Архитектура:**

- `core/doctor/DiagnosticStep.kt` — enum шагов и статусов (`OK`, `WARN`, `FAIL`, `SKIP`).
- `core/doctor/DiagnosticResult.kt` — результат шага: статус, безопасное описание, длительность, `Remedy`.
- `core/doctor/Remedy.kt` — sealed-класс действий и их класс безопасности: `SAFE_AUTO` (`Recheck`, `OpenSettings`, `RefreshSubscription`) и `REQUIRES_CONFIRM` (`SwitchServer`, `ReimportProfile`, `RestartCore`, `ChangeDns`, `EnableTlsFragment`).
- `core/doctor/ConnectionDoctor.kt` — оркестратор: последовательные шаги, таймауты, отмена, повторный запуск.
- `core/doctor/RemedyExecutor.kt` — выполняет лечение через существующие репозитории и координатор.
- `core/doctor/DoctorReport.kt` — безопасный отчёт для экспорта.
- `ui/doctor/DoctorScreen.kt`, `DoctorViewModel.kt`.

Существующий пакет `core/diagnostics` (`BatteryLogger`, `BatteryMonitor`, `DeviceIdManager`) не трогаем и не смешиваем с Доктором.

**Контракты:**

- Doctor не запускается автоматически при каждом коннекте. Только по кнопке «Проверить» или после fail.
- Doctor не меняет активный сервер, DNS и параметры фрагментации автоматически. DNS — только показ состояния и переход в настройки; фрагментация/uTLS — только через раздел «Устойчивость» по явному действию пользователя.
- `SAFE_AUTO`-лечения выполняются по кнопке; `REQUIRES_CONFIRM` — только после явного согласия.
- Doctor не хранит секреты; отчёт проходит sanitizer.
- Общий таймаут — 45 с; шаги 3–5 могут идти параллельно.
- Доктор не блокирует первичный Connect и не запускается до первой ошибки, если пользователь не нажал кнопку.

**Тесты:** pure-логика статусов и приоритета лечения; fake-репозитории для шагов; проверка, что отчёт не содержит секретов.

**Риски:** ложные диагнозы; замедление; сложность воспроизведения. Смягчение: статус `WARN` вместо `FAIL`, если данных недостаточно; возможность «пропустить шаг».

### 3.2 «Проверка сервисов» — доступность того, зачем включили VPN

**Сценарий:** пользователь нажимает «Проверить сервисы» и видит: YouTube — работает, Telegram — работает, ChatGPT — нет. Понимает, что проблема не в VPN вообще, а в конкретном сервисе/сервере.

**Архитектура:**

- `core/services/ServiceCatalog.kt` — список сервисов: id, название, категория, endpoint, метод, иконка. Endpoint'ы нейтральные, без авторизации.
- `core/services/ServiceChecker.kt` — проверка через локальный mixed inbound (`127.0.0.1:10809`), последовательно или с ограниченным параллелизмом (3). Один и тот же чекер используется экраном «Проверка сервисов» и шагом 9 Доктора.
- `core/services/ServiceCheckResult.kt` — `serviceId`, `reachable`, `latencyMs`, `httpCode`, `checkedAt`, `reason`.
- `ui/services/ServicesScreen.kt`, `ServicesViewModel.kt` — сетка, статусы, «проверить всё», объяснение.

**Правила:**

- Проверка только при активном VPN; иначе предложить подключиться.
- Не логировать URL и результаты по конкретным сервисам в общий journal; только агрегат.
- Не обещать «сервис работает» — только «контрольный запрос прошёл».
- Каталог расширяемый; пользователь может отключить категории.

**Стартовый каталог:** YouTube, Telegram, WhatsApp, Instagram, ChatGPT, Google, GitHub, банковская категория (нейтральный endpoint). Точные endpoint'ы — в коде, без секретов.

**Тесты:** парсинг каталога, таймауты, поведение без VPN, отсутствие URL в логах.

**Риски:** зависимость от внешних endpoint; ложные «не работает» при блокировке самого endpoint. Смягчение: 2 попытки, разный метод, статус «не удалось проверить» вместо «не работает».

### 3.3 «Автопилот обхода» — автоматическая устойчивость к DPI

**Сценарий:** в «сложной» сети сервер не подключается. Автопилот сам пробует фрагментацию TLS, другой fingerprint, другой транспорт и сообщает, что сработало.

**Что уже есть:** `DurabilitySettings`, `DurabilityOptions`, `tlsFragment`, `tlsRecordFragment`, `uTLS`, `native urltest`. Всё закрыто `DebugFlags.diagnosticEnabled()`.

**Что делаем:**

- Выводим настройки в обычный UI: раздел «Устойчивость» с пресетами.
- `core/durability/BypassProfile.kt` — `NORMAL`, `HARD_NETWORK`, `MAXIMUM_STEALTH`.
- `core/durability/BypassOrchestrator.kt` — при неудаче handshake перебирает до 4 комбинаций с ограничением по времени и батарее.
- Интеграция: после fail `NetworkTimeout`/TLS-ошибки — предложение «Попробовать автопилот»; в настройках — «включать автоматически».
- Логирование: только факт «сработала комбинация №N», без параметров сервера.

**Правила:**

- Golden path остаётся первым.
- Автопилот не работает в фоне бесконечно; максимум 4 попытки, затем понятная ошибка.
- Не включать `MAXIMUM_STEALTH` по умолчанию: выше расход и риск несовместимости.
- Уважать `BatteryPolicy`: в saver — только 1 попытка.

**Тесты:** перебор комбинаций, лимиты, отмена, отсутствие секретов в логах.

**Риски:** замедление, батарея, несовместимость с сервером. Смягчение: лимиты, откат, явный статус.

---

### 3.4 «Переезд в один клик» — миграция из конкурентов

**Сценарий:** пользователь приходит из Happ/v2rayNG/Hiddify, нажимает «Перенести», выбирает файл/буфер/QR и получает свои серверы и настройки.

**Архитектура:**

- `core/migration/MigrationSource.kt` — `HAPP`, `V2RAYNG`, `HIDDIFY`, `KARING`, `NEKOBOX`, `V2BOX`, `CLASH`, `URI_LIST`, `QR`.
- `core/migration/MigrationDetector.kt` — определяет источник по сигнатурам (JSON-схема, YAML, base64, URI).
- `core/migration/MigrationImporter.kt` — нормализует в `ParsedConfig`, дедуп по `connectionKey()`, отчёт.
- `core/migration/MigrationReport.kt` — получено/распознано/отклонено/дубликаты, без секретов.
- `ui/migration/MigrationScreen.kt`, `MigrationViewModel.kt`.

**Правила:**

- Не читать чужие данные без явного выбора пользователя.
- Не сохранять исходные файлы дольше операции.
- Не логировать содержимое.
- Импортированные профили сохраняются только через `EncryptedSharedPreferences` + Android Keystore, как обычные.
- Поддерживать частичный импорт: если 3 из 20 не распознаны — импортировать 17 и показать отчёт.

**Тесты:** fixtures без реальных ключей; определение источника; дедуп; отчёт.

**Риски:** форматы меняются; лицензии. Смягчение: собственные парсеры, без копирования чужого кода.

---

### 3.5 «Приватность, которую видно»

**Сценарий:** пользователь открывает «Приватность» и видит: что хранится, где, куда уходит, что не уходит. Может экспортировать отчёт с предпросмотром.

**Архитектура:**

- `core/privacy/PrivacyFacts.kt` — факты: хранилища, permissions, сетевые вызовы, телеметрия, crash reporting.
- `core/privacy/PrivacyReportBuilder.kt` — собирает отчёт из конфигурации и настроек.
- `ui/privacy/PrivacyScreen.kt` — экран и экспорт с preview.
- `docs/PRIVACY_REPORT.md` — публичный документ.
- CI: reproducible build job (отдельная волна), SBOM уже есть.

**Правила:**

- Отчёт не содержит секретов и реальных адресов.
- Все утверждения проверяемы по коду.
- Телеметрия и crash reporting — только opt-in, по умолчанию off.

**Тесты:** sanitizer, состав отчёта, отсутствие секретов, unit-тест соответствия отчёта реальным флагам и настройкам.

**Риски:** обещания расходятся с кодом. Смягчение: отчёт генерируется из тех же флагов, что и поведение.

---

### 3.6 «Незаметная надёжность» — роуминг и батарея

**Сценарий:** пользователь идёт с Wi-Fi на LTE, VPN не рвётся; за ночь батарея не умирает.

**Что уже есть:** `NetworkAwareReconnector`, `BatteryPolicy`, `HealthMonitor`, `AutoSwitcher` с cooldown/hysteresis.

**Что делаем:**

- `core/network/RoamingPolicy.kt` — pure-логика поверх существующего `NetworkAwareReconnector`, а не второй механизм reconnect. Единая точка решения: когда reconnect, когда ждать, когда переключить сервер.
- Профили питания: «Скорость», «Баланс», «Батарея» — влияют на интервалы и глубину проб.
- Уведомление о деградации: «Сеть ухудшилась, переключаюсь на резервный сервер» с возможностью отменить.
- Always-on/kill switch: проверка конфигурации и понятный статус.

**Правила:**

- Не переподключаться при кратковременном дребезге сети.
- Не будить радио без необходимости.
- Не менять сервер без подтверждения, если это не hard failure.

**Тесты:** pure-политика, сценарии Wi-Fi↔LTE, Doze, saver.

**Риски:** OEM-агрессия, батарея. Смягчение: device-тесты, откат, настройки.

---

### 3.7 «Шлюз для ТВ и ноутбука»

**Сценарий:** телефон раздаёт интернет, а ТВ/ноутбук подключается к локальному прокси по QR.

**Архитектура:**

- `core/gateway/LocalGateway.kt` — HTTP/SOCKS прокси на локальном интерфейсе, привязка к Wi-Fi/hotspot. Отдельный порт, не `10809` (он занят mixed inbound); при старте проверять конфликт.
- `core/gateway/GatewayConfig.kt` — порт, логин/пароль, разрешённые подсети.
- `ui/gateway/GatewayScreen.kt` — включение, QR, инструкция, предупреждение.
- `core/gateway/GatewayQr.kt` — QR с настройками.

**Правила:**

- Только Wi-Fi/hotspot, не публичный интернет.
- Случайный пароль, смена при каждом включении.
- Явное предупреждение о безопасности.
- Автоотключение при смене сети/выключении VPN.

**Тесты:** генерация конфига, QR, запрет на публичные интерфейсы.

**Риски:** безопасность, батарея. Смягчение: ограничения, предупреждения, автоотключение.

### 3.8 «Профили под задачу»

**Сценарий:** пользователь выбирает «Стриминг» / «Работа» / «Приватность» / «Обход» — и приложение меняет веса выбора сервера и маршрутизацию.

**Архитектура:**

- `core/profile/UsageProfile.kt` — enum с весами и правилами.
- `core/profile/ProfilePolicy.kt` — применяет веса к `ScoringEngine`, выбирает `RoutingPreset`.
- UI: компактный селектор на главном экране.
- Тесты: веса, приоритеты, fallback.

**Правила:**

- Профиль не блокирует ручной выбор.
- «Приватность» не включает ничего, что ломает соединение.
- «Обход» не обещает обход всего.

**Риски:** переусложнение. Смягчение: 4 профиля, понятные подписи.

## 4. Волны внедрения

### Волна 1 — быстрые видимые победы (0–2 недели)

Волна разбита на три независимых шага, каждый — отдельный коммит и проверка.

**1a. Проверка сервисов (3.2)** — самая быстрая и заметная. Только активный mixed inbound, статус `VPN_OFF` без VPN, два attempt'а, без URL в журнале.

**1b. Автопилот обхода (3.3)** — снять debug-гейт, вывести пресеты, добавить `BypassOrchestrator` с лимитом попыток и перезапуском core.

**1c. Каркас Доктора (3.1)** — модель шагов, 4 безопасных шага (подписка, профиль, TCP, трафик), экран и вход из меню «Ещё».

**DoD:** фичи доступны, тесты зелёные, CI зелёный, Golden path не изменён, документация обновлена.

### Волна 2 — глубина и рост (2–5 недель)

4. **Доктор полностью** (3.1): все 9 шагов, автолечение, отчёт.
5. **Переезд** (3.4): 3 источника в первой итерации (Happ, v2rayNG, Clash), затем остальные.
6. **Приватность** (3.5): экран, отчёт, экспорт с preview.

**DoD:** импорт из 3 источников, отчёт Доктора без секретов, privacy-экран.

### Волна 3 — надёжность и персонализация (5–10 недель)

7. **Роуминг и батарея** (3.6): политика, профили питания, уведомления.
8. **Профили под задачу** (3.8): 4 профиля, интеграция со скорингом.

**DoD:** device-тесты Wi-Fi↔LTE, battery baseline, профили не ломают ручной выбор.

### Волна 4 — ниша (после)

9. **Шлюз** (3.7): локальный прокси, QR, ограничения.

**DoD:** безопасность подтверждена, автоотключение, документация.

## 5. Архитектура и границы

```
ui/<feature>            Compose + ViewModel
  ↓
core/<feature>          use cases, pure logic
  ↓
существующие сервисы    ConnectionCoordinator, SingBoxCore, SubscriptionRepository,
                        DeepProbeEngine, TrafficValidator, HealthChecker
```

**Новые пакеты:**

- `core/feature` — `FeatureFlags` с дефолтами `false`
- `core/doctor` — диагностика (не путать с существующим `core/diagnostics`)
- `core/services` — каталог и проверка сервисов
- `core/durability` — расширение существующего `DurabilitySettings`
- `core/migration`
- `core/privacy`
- `core/gateway`
- `core/profile`

**Правила:**

- Core не зависит от Compose.
- ViewModel не содержит сетевой логики.
- Все новые сетевые вызовы — через существующие клиенты с таймаутами.
- Все новые настройки — через `SettingsViewModel` и SharedPreferences/EncryptedSharedPreferences по чувствительности.
- Фича-флаги: `FeatureFlags` с дефолтами `false` для рискованных.

## 7. Риски программы

| Риск | Вероятность | Влияние | Смягчение |
|---|---|---|---|
| Ложные диагнозы Доктора | средняя | высокое | WARN вместо FAIL, пропуск шага, отчёт |
| Автопилот замедляет коннект | средняя | среднее | лимит 4 попытки, только после fail |
| Импорт ломает профили | низкая | высокое | валидация, отчёт, откат |
| Приватность-обещания расходятся с кодом | низкая | высокое | генерация из флагов, аудит |
| Роуминг жрёт батарею | средняя | среднее | профили, baseline, device-тесты |
| Шлюз открывает доступ | низкая | критическое | только Wi-Fi, пароль, автоотключение |
| Перегрузка UI | средняя | среднее | один экран — одна задача, настройки вглубь |

## 8. Что не делаем

- Не строим свою сеть серверов и не добавляем встроенные подписки.
- Не добавляем телеметрию, аккаунты и облачную синхронизацию по умолчанию.
- Не гонимся за количеством протоколов и кроссплатформенностью.
- Не копируем UI и код конкурентов.

## 9. Definition of Done программы

1. Код в `task/breakthrough-program`, разбит на логические коммиты.
2. Тесты: unit + fake-интеграция; device-проверки отмечены честно.
3. CI зелёный: build, tests, CodeQL, SBOM.
4. Документация: эта фича, как включить, какие ограничения.
5. Метрика фичи определена и считается локально.
6. Аудит: `APPROVE` от аудитора.
7. Merge в `main` — только после подтверждения пользователя.

---

## 10. Порядок работ

1. Зафиксировать план (этот документ) — коммит.
2. Аудит-конференция: `auditor-deepseek`, `auditor-mimo`, `auditor-nemotron`.
3. Свести отчёты, обновить план.
4. Волна 1: код, тесты, сборка.
5. Аудит волны 1, исправления.
6. PR, CI, merge после подтверждения.
7. Волны 2–4 по тому же циклу.
