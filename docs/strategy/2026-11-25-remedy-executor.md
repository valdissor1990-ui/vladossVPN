# Волна 2.1: исполнение лечений Доктора (`RemedyExecutor`)

**Дата:** 2026-11-25
**Ветка:** `task/remedy-executor` (база — `task/connection-doctor`)
**Файлы:** `core/doctor/RemedyExecutor.kt`, `core/doctor/RemedyExecutorTest.kt`

## 1. Проблема

До этой волны Доктор умел только показывать текст действия («Сменить сервер», «Обновить подписку»), но не выполнять его. Пользователь видел диагноз и должен был сам искать нужный экран. Это ровно та претензия, которую пользователи предъявляют диагностическим экранам конкурентов: «нашёл проблему — иди разбирайся сам».

## 2. Что сделано

Введён порт `RemedyActions` — единственный способ, которым ядро Доктора может вызвать побочный эффект:

```kotlin
interface RemedyActions {
    suspend fun refreshSubscription(): RemedyActionResult
    suspend fun restartCore(): RemedyActionResult
    suspend fun switchServer(): RemedyActionResult
    suspend fun reimportProfile(): RemedyActionResult
}
```

Реализацию даёт прикладной слой: те же репозитории и координатор, что используют остальные экраны. Ядро Доктора остаётся без Android и тестируется с фейками.

`RemedyExecutor.execute(remedy, confirmed)` возвращает один из исходов:

| Исход | Когда |
|---|---|
| `PERFORMED` | действие выполнено и вернуло успех |
| `NEEDS_CONFIRM` | `REQUIRES_CONFIRM` без явного подтверждения — ничего не запускалось |
| `DELEGATED_TO_UI` | «Проверить снова», «Открыть настройки», «DNS», «Фрагментация TLS» — это навигация, экран делает сам |
| `FAILED` | действие вернуло ошибку или бросило исключение |
| `UNSUPPORTED` | реализация ещё не подключена |
| `BUSY` | другое действие уже выполняется — второй вызов ничего не запустил |
| `REFUSED` | действие сейчас небезопасно (рестарт во время установки туннеля) |

## 3. Правила безопасности

- `SAFE_AUTO` выполняется по нажатию кнопки, но не автоматически после диагностики.
- `REQUIRES_CONFIRM` без `confirmed = true` не трогает ни сервер, ни ядро, ни DNS.
- Смена DNS и фрагментация TLS **не выполняются** исполнителем даже с подтверждением: он только ведёт в соответствующий раздел, где решение принимает пользователь. Это чистая навигация, поэтому они помечены `SAFE_AUTO` и не прячутся за лишним диалогом.
- `RefreshSubscription` остаётся `SAFE_AUTO`: он перечитывает подписку пользователя, но не меняет активный профиль и не перезапускает ядро.
- Повторное нажатие во время работы даёт `BUSY`: исполнитель держит `Mutex` на всё действие, поэтому два тапа не запускают два рестарта или две перезаписи подписки.
- `RestartCore` возвращает `REFUSED`, если переданный предикат `isRestartAllowed()` говорит, что туннель устанавливается.
- `CancellationException` пробрасывается — уход с экрана отменяет действие, а не превращается в «не удалось».
- Причина отказа — фиксированный код `RemedyFailure` (`NETWORK`, `TIMEOUT`, `REJECTED`, `BAD_STATE`, `UNKNOWN`), а не сырой текст. Текст исключения не попадает ни в UI, ни в журнал: в журнал пишется только класс исключения, потому что сообщения движка могут содержать адрес и имя профиля.
- Если действие упало после частичного эффекта, сообщение говорит «не удалось подтвердить результат», а не «ничего не произошло».

## 4. Как подключать к UI (следующий шаг)

1. Hilt-модуль: `RemedyActions` ← реализация на `SubscriptionRepository` и `ConnectionCoordinator`.
2. В `DoctorViewModel` добавить `remedyExecutor` и событие `onRemedyPressed(remedy)`: для `REQUIRES_CONFIRM` сначала показать диалог, затем вызвать с `confirmed = true`.
3. Результат показать строкой состояния; после `PERFORMED` для `RefreshSubscription`/`SwitchServer` предложить «Проверить снова».
4. Не запускать `RestartCore`, пока VPN в `Connecting`/`Verifying`: передайте в `RemedyExecutor` предикат `isRestartAllowed`; при `false` вернётся `REFUSED` и порт не будет вызван.

## 5. Тесты

`RemedyExecutorTest` покрывает: `SAFE_AUTO` без подтверждения; отказ для **каждого** `REQUIRES_CONFIRM` без согласия и выполнение с ним; делегирование навигации (включая DNS и TLS) без диалога и без вызова порта; `UNSUPPORTED`; `FAILED` с фиксированным кодом; `REFUSED` для рестарта при установке туннеля; `BUSY` при повторном нажатии и разблокировку после завершения; отсутствие утечки текста исключения в сообщение и журнал (журнал получает только класс); проброс отмены.

## 6. Границы

- Исполнитель не решает, какое лечение предложить: это по-прежнему `ConnectionDoctor`.
- Исполнитель не проверяет результат лечения: после действия нужен повторный прогон Доктора, иначе «выполнено» — это только факт вызова, а не подтверждённое исправление.
- QoS/агрессивные действия (смена DNS, TLS-фрагментация) сознательно оставлены человеку.
