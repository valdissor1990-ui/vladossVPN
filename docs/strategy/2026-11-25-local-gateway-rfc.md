# RFC: локальный шлюз для ТВ и ноутбука (`LOCAL_GATEWAY_ENABLED`)

**Дата:** 2026-11-25
**Статус:** проект, реализация не начата
**Связано:** волна 3.7 программы прорыва
**Флаг:** `FeatureFlags.LOCAL_GATEWAY_ENABLED = false` — в тестовый релиз не включается

---

## 1. Задача и границы

Телефон с активным VPN раздаёт интернет по Wi-Fi/hotspot, а ТВ/ноутбук подключается к нему как к HTTP/SOCKS-прокси по QR. Пользователь не должен вручную вводить IP, порт и пароль.

Вне границ: публикация шлюза в интернет, работа без активного VPN, доступ к панели управления VPN по сети, Play-флейвор.

## 2. Почему это отдельный RFC, а не просто inbound

Три технических препятствия, каждое из которых ломает «наивную» реализацию:

1. **Return-path LAN-клиентов.** Ответ LAN-клиенту адресован на его IP в подсети hotspot. При `auto_route`/`strict_route` этот адрес уйдёт в TUN, и клиент зависнет, потому что ответ придёт не туда. Нужен `route_exclude_address`/`exclude` на подсеть клиентов **до** сборки golden-конфига.
2. **Новый inbound в golden-конфиге.** Сейчас golden-путь — один `mixed` на `127.0.0.1:10809` (`SingboxConfigBuilder.PROXY_PORT`). Добавление второго inbound на `0.0.0.0` меняет поверхность атаки и должно быть выключено по умолчанию, а не «при включённом флаге в проде».
3. **Секрет в конфиге.** Пароль попадает в JSON конфига sing-box. Он не должен оказаться в логах, в `dumpsys`, в crash-report и в обычных `SharedPreferences`.

## 3. Архитектура

```
core/gateway/
  GatewayConfig.kt      — неизменяемая модель: порт, логин, способ генерации пароля, разрешённая подсеть
  GatewaySecretStore.kt — EncryptedSharedPreferences (androidx.security-crypto), MasterKey AES256-GCM
  GatewayAddress.kt     — выбор локального адреса: Wi-Fi или hotspot, только RFC1918, явный отказ на публичный
  LocalGateway.kt       — жизненный цикл: validate → build inbound → start → stop, привязка к VPN-сессии
  GatewayQr.kt          — QR-полезная нагрузка, без изображения: только строка, рендер в UI
ui/gateway/
  GatewayScreen.kt      — включение, предупреждение, «показать пароль», QR по кнопке
```

### 3.1 Конфиг

| Поле | Значение по умолчанию | Ограничение |
|---|---|---|
| `port` | 0 (свободный из диапазона 20000–29999) | не 10809 и не порт ядра; проверка занятости на старте |
| `listen` | локальный адрес Wi-Fi/hotspot | только RFC1918 |
| `username` | `vladoss` | фиксированный, не секрет |
| `password` | 24 символа base32 (120 бит) | новый при каждом включении |
| `allowedSubnet` | подсеть текущего интерфейса | одна, не `/0` |
| `type` | `http` | SOCKS не включаем в первой итерации |

### 3.2 Жизненный цикл

- Шлюз стартует **только** когда VPN в `Connected`; подписка на состояние соединения.
- VPN ушёл из `Connected` → шлюз закрывается, активные соединения получают `407 Proxy Authentication Required`, а не тишину.
- Смена сети/выключение Wi-Fi → автоотключение, новое включение только вручную.
- Смена пароля при каждом включении; старый пароль невалиден сразу.
- Отдельный поток/диспетчер; никаких блокирующих вызовов в главном.

### 3.3 Потокобезопасность и лимиты

- Максимум 16 одновременных клиентских соединений, очередь 32, иначе явный отказ.
- Таймаут установления соединения 15 с, простоя 5 мин.
- Лимит на размер заголовков (16 КБ) и на число заголовков (64) — защита от мусора в локальной сети.
- Логи: только факт старта/остановки и счётчики. Логин, пароль и полный URL никогда не пишутся.

## 4. Интеграция с sing-box

Новый inbound добавляется **только** в собранный конфиг при включённом флаге:

```json
{ "type": "http", "tag": "gateway-in", "listen": "<lan-ip>", "listen_port": <port>,
  "users": [{ "username": "vladoss", "password": "<generated>" }] }
```

Правила:

- `route.rules` получает `exclude`/`route_exclude_address` на `allowedSubnet` с более высоким приоритетом, чем `tun`-маршрут.
- Исключение подсети добавляется в TUN-настройки, а не в правила маршрутизации только: этого требует return-path.
- Конфликт порта с `PROXY_PORT` (10809) и с портом core-API — жёсткая ошибка конфигурации, а не «попробуем ещё раз».
- Проверка, что итоговый JSON валиден, выполняется тем же путём, что и golden-конфиг; отдельного «доверенного» парсера нет.

## 5. Флейворы и политика

- Флаг включается **только** в `direct` (не Play), потому что шлюз — это локальный сервер на устройстве. В Play-флейворе `LOCAL_GATEWAY_ENABLED` остаётся `false`, UI-экран не показывается.
- В тестовый релиз флаг не включается: в первом прогоне нужен device-отчёт, а не широкая раздача.

## 6. Безопасность и предупреждения

- Явный экран-предупреждение при первом включении: «Любой в этой Wi-Fi-сети, кто знает пароль, получит доступ к вашему VPN».
- Пароль скрыт, показ — отдельной кнопкой.
- QR — отдельной кнопкой, с предупреждением, что скриншот раскрывает доступ; QR не сохраняется на диск.
- `GatewaySecretStore` — `EncryptedSharedPreferences` с `MasterKey` AES256-GCM; обычные `SharedPreferences` не используются.
- Пароль стирается из памяти при выключении шлюза (обнуление массива символов, где это возможно).

## 7. Тесты

| Уровень | Что проверяем |
|---|---|
| Unit | `GatewayAddress` отказывает на публичный IP, `10.x/172.16–31/192.168` принимает |
| Unit | генерация пароля: длина, алфавит, уникальность между включениями |
| Unit | сборка inbound: порт не равен 10809, поля `users` заполнены |
| Unit | `route_exclude_address` содержит подсеть клиентов и имеет приоритет над TUN |
| Unit | VPN не `Connected` → `start` отказывает с явной ошибкой |
| Unit | остановка шлюза при потере `Connected` даёт `407` |
| Unit | логи не содержат пароль (тест на перехваченный логгер) |
| Device | ТВ/ноутбук через QR открывает страницу, отключаем VPN — соединение закрывается с ошибкой |

## 8. Этапы

1. `GatewayConfig` + `GatewaySecretStore` + unit-тесты (без сети).
2. `GatewayAddress` + отказ на публичные интерфейсы.
3. Сборка inbound + `route_exclude_address`, проверка конфликта портов.
4. `LocalGateway` жизненный цикл + `407` при потере VPN, лимиты соединений.
5. `GatewayQr` + `GatewayScreen` под флагом.
6. Device-прогон на реальном ТВ/ноутбуке, отчёт, только затем обсуждение включения флага.

## 9. Открытые вопросы

- Нужен ли SOCKS5 в первой итерации (некоторые ТВ умеют только SOCKS)?
- Как вести себя при нескольких LAN-интерфейсах (Wi-Fi + USB-tethering) — один шлюз на интерфейс или отказ?
- Нужен ли журнал подключений клиентов (IP + время) или достаточно счётчиков?
