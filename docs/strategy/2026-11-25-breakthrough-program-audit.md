# Аудит программы прорыва — 2026-11-25

**Статус:** аудит-конференция: 2 отчёта из 3 + самоаудит. Оба аудитора — `REQUEST CHANGES`  
**Причина:** `auditor-mimo` не смог завершить работу — исчерпан лимит бесплатной модели. `auditor-deepseek` и `auditor-nemotron` отчёты выдали.  
**Проверяемый документ:** `docs/strategy/2026-11-25-breakthrough-program.md`  
**Метод:** чтение плана, ключевого кода (`HealthChecker`, `TrafficValidator`, `SingboxProxyClient`, `DurabilitySettings`, `VpnProxyService`, `HomeViewModel`, `ConnectionCoordinator`, `SubscriptionRepository`) и проверка конфликтов.

---

## 1. Находки

### Critical

**C1. Автопилот обхода не работает в release.**  
`DurabilitySettings.load()` возвращает `DurabilityOptions()` при `!DebugFlags.diagnosticEnabled()`, а `diagnosticEnabled()` = `BuildConfig.DEBUG && DIAGNOSTIC_MODE`. В release-сборке все настройки игнорируются. Без снятия этого gate фича «Автопилот обхода» существует только в debug.  
**Решение:** убрать зависимость от `BuildConfig.DEBUG` для пользовательских настроек устойчивости. По умолчанию все флаги остаются `false`, поэтому golden path не меняется. Debug-гейт оставить только для диагностических экранов.

**C2. Проверка сервисов требует активного VPN, но не должна запускать второй core.**  
`HealthChecker.testLatency()` при активном VPN сознательно падает (`Cannot probe an alternative profile while the VPN core is active`). Для проверки сервисов нужен путь через уже работающий mixed inbound, как в `TrafficValidator`/`testActiveTunnelLatency`. Запускать временный Sing-box на каждый сервис нельзя: дорого, конфликтует с `CorePortLease`.  
**Решение:** отдельный `ServiceChecker`, который работает только при `VpnProxyService.isRunning && !isCoreTransitioning` и ходит через `127.0.0.1:PROXY_PORT`. Если VPN не активен — статус `VPN_OFF`, без попыток подключения.

**C3. Применение новых durability-настроек требует перезапуска core.**  
`VpnProxyService` читает `DurabilitySettings.load()` один раз при старте (строка ~537). Изменение настроек на лету не применится.  
**Решение:** `BypassOrchestrator` меняет настройки и вызывает штатный reconnect через существующий путь, а не пытается менять конфиг активного ядра. Пользователю показывать «потребуется переподключение».

### High

**H1. Доктор не должен смешивать шаги, требующие остановки core, с безопасными.**  
`DeepProbeEngine` требует эксклюзивный `CorePortLease` и остановленный VPN. Если Доктор запустит preflight при активном VPN, он либо упадёт, либо даст ложный результат.  
**Решение:** разделить шаги на `SAFE_WHILE_CONNECTED` (DNS, TCP, TLS-hint, трафик, сервисы) и `REQUIRES_CORE_STOP` (preflight профиля). В волне 1 — только безопасные шаги. Полный preflight — отдельной кнопкой с предупреждением.

**H2. Лечение не должно менять сервер или настройки без подтверждения.**  
Автоматическая смена сервера ломает обещание «приложение не заменяет активный сервер молча» из `PRODUCT_STRATEGY.md`.  
**Решение:** `Remedy` делится на `SAFE_AUTO` (DNS, повторная проверка, открытие настроек) и `REQUIRES_CONFIRM` (смена сервера, переимпорт, перезапуск). `SAFE_AUTO` выполняется по кнопке, `REQUIRES_CONFIRM` — только после явного согласия.

**H3. `InetAddress.getByName` может блокироваться и не иметь таймаута.**  
На Android DNS-резолв может висеть десятки секунд.  
**Решение:** `withTimeout(3_000)` + `Dispatchers.IO`; при таймауте — `WARN`, не `FAIL`.

**H4. Проверка сервисов может давать ложные «не работает».**  
Endpoint может быть заблокирован сам по себе, CDN может отдавать 403 на HEAD, captive portal может подменять ответ.  
**Решение:** два метода (HEAD, затем GET с `Range: bytes=0-0`), два attempt'а, статус `UNKNOWN` вместо `FAIL`, если оба раза ошибка сети, а не HTTP-код. В UI формулировка «контрольный запрос не прошёл», а не «сервис заблокирован».

**H5. Приватность проверки сервисов.**  
Нельзя писать в journal URL, host и результат по каждому сервису: это раскрывает, что пользователь проверяет.  
**Решение:** в journal только агрегат `checked=N, reachable=M`; `ServiceCheckResult` хранит `serviceId`, не URL. Экспорт отчёта — без endpoint'ов.

**H6. Новые входы перегрузят главный экран.**  
`HomeScreen` уже 33 КБ и содержит меню, рекомендации, список серверов, статистику.  
**Решение:** входы в «Проверить сервисы» и «Диагностику» — в существующее меню «Ещё» (рядом с «Журнал логов» и «Настройки»). На главный экран не добавлять новые кнопки в волне 1.

### Medium

**M1. Волна 1 слишком большая для одного цикла.**  
Три направления в одной волне затрудняют аудит и merge.  
**Решение:** разбить: 1a — Проверка сервисов, 1b — Автопилот обхода, 1c — каркас Доктора. Каждая — отдельный коммит и проверка.

**M2. `MigrationDetector` может ошибиться в формате.**  
Автоопределение источника по сигнатурам ненадёжно.  
**Решение:** пользователь явно выбирает источник; автоопределение — только подсказка. Всегда показывать отчёт до сохранения.

**M3. Локальный шлюз — критический риск безопасности.**  
Открытый прокси в локальной сети может стать точкой входа.  
**Решение:** только Wi-Fi/hotspot, случайный пароль, автоотключение при смене сети, явное предупреждение, запрет на публичные интерфейсы. Волна 4, не раньше.

**M4. Профили под задачу могут усложнить выбор.**  
Четыре профиля + рекомендация + ручной выбор — риск перегрузки.  
**Решение:** профиль меняет только веса рекомендации, не блокирует ручной выбор; подпись «влияет на рекомендацию».

**M5. Роуминг может дублировать существующий `NetworkAwareReconnector`.**  
В проекте уже есть обработка смены сети и `NetworkBucketProvider`.  
**Решение:** не создавать второй reconnect-механизм; расширять существующий pure-политикой и тестами.

### Low

**L1. Иконки сервисов.** Брендовые логотипы — лицензионный риск. Использовать буквы/цветные кружки или Material Icons.  
**L2. Названия.** «Проверка сервисов» понятнее, чем «Service Check». В коде — `ServiceCheck`, в UI — русские подписи.  
**L3. Тесты.** Для `ServiceChecker` нужен fake HTTP-клиент; для `ConnectionDoctor` — fake шаги; для `BypassOrchestrator` — fake reconnect. Иначе тесты будут тянуть Android.

| Severity | Находка | Решение |

| high | `403/429` показывались красным «не прошёл», хотя ответ дошёл: `chatgpt.com/robots.txt` стабильно отдаёт `403`. Это ложный вывод «заблокировано». | Введён статус `ANSWERED` («сервер ответил N — туннель работает»), 4xx/5xx больше не красятся в провал. |

## 1.10 Волна 1b: пресеты устойчивости (реализовано)

| Что | Файл |
|---|---|
| Пресеты `NORMAL`, `HARD_NETWORK`, `MAXIMUM_STEALTH` + состояние `CUSTOM` только для честного отображения ручных настроек | `core/durability/BypassProfile.kt` |
| Автопилот: две смены пресета, затем остановка; без собственных ретраев и таймеров | `core/durability/BypassOrchestrator.kt` |
| Экран выбора профиля с честным «применится после переподключения» и обновлением при внешнем изменении prefs | `ui/durability/DurabilityScreen.kt`, `DurabilityViewModel.kt` |
| Вход из настроек, секция «Устойчивость» | `SettingsScreen.kt`, `MainActivity.kt` (маршрут `durability`) |
| Интеграция: только retryable-ошибка, один шаг пресета и одна автоматическая попытка без прав ручного подключения | `HomeViewModel.kt` |

Правила соблюдены:
- `NORMAL` сбрасывает только транспортную маскировку (фрагментация и отпечаток); urltest и остальные настройки сохраняются;
- пресет меняет только транспортные флаги, сервер/DNS/маршруты не трогает;
- своих ретраев нет: автопилот делает одну попытку за ошибку, лимит `MAX_ATTEMPTS = 2` (ровно две ступени лестницы), при успехе или ручном подключении счётчик сбрасывается;
- автоматическая попытка отправляет `ConnectRequested(userInitiated = false)`: не снимает fatal-lock, не чистит историю отказов эндпоинтов и не показывает повторный запрос разрешения VPN;
- автопилот реагирует только на `Error.retryable = true`; отказ в разрешении, конфликт TUN, «нет серверов» и незавершённая остановка ядра его не запускают;
- при активном fatal-lock автопилот останавливается и показывает понятное уведомление; при исчерпании лестницы — тоже;
- `detect` не выдаёт ручную комбинацию за готовый пресет: для неё есть `CUSTOM`, и автопилот её не перезаписывает;
- явная остановка пользователем отменяет шаг автопилота и запрещает поздним ошибкам запускать тоннель;
- по умолчанию `BYPASS_AUTOPILOT_ENABLED = false`: автоматика не работает до аудита, ручной выбор профиля доступен всегда и безопасен;
- журнал пишет только имя профиля и номер попытки, без адресов.

Тесты: `BypassProfileTest` (9), `BypassOrchestratorTest` (5), включая реалистичную последовательность `load → nextProfile → applyTo → save` и остановку на `CUSTOM`.

Открыто до включения флага: проверка на устройстве, что смена пресета действительно применяется после переподключения ядра, и покрытие `HomeViewModel` интеграционным тестом (сейчас в проекте нет тестового каркаса для него).
