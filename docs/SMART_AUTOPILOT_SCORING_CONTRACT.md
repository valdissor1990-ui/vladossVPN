# Smart Autopilot: контракт измерений и принятия решений

Статус: проектное решение для P2.2, не реализация. Документ основан на статическом просмотре исходников `ServerScanner`, `DeepProbeEngine`, `HealthChecker`, `ScoringEngine`, `AutoSwitcher`, `SwitchDecisionEngine`, `ConnectServerSelector` и `SingboxConfigBuilder`.

## 1. Главный принцип

Нельзя сравнивать значения, полученные разными способами, в разное время или через разные сетевые маршруты, как будто это одна и та же метрика.

В приложении должны быть явно разделены три вида измерений:

1. **Preflight профиля** — отдельная проверка каждого профиля через его собственный outbound, пока основной VPN остановлен.
2. **Health-check активного туннеля** — запрос через уже работающий локальный mixed inbound. Он измеряет текущий маршрут целиком, но не сравнивает сервер с альтернативами.
3. **Deep diagnostic** — расширенная проверка latency, jitter, packet loss и throughput. Дороже по времени и трафику; не должна автоматически запускаться в обычном цикле мониторинга.

## 2. Контракт по этапам

| Этап | Что измеряем | Допустимое применение |
|---|---|---|
| Импорт | Формат, число кандидатов, поддерживаемые профили, ошибки | Объяснить результат импорта; не выбирать сервер |
| Preflight | Успешность HTTP-проб, median RTT по профилю | Первичный выбор и список проверенных резервов |
| Подключение | Установление ядра + фактический трафик через VPN | Подтвердить, что выбранный профиль действительно работает |
| Активный health-check | RTT через локальный mixed inbound, последовательная динамика RTT/jitter | Определить деградацию текущего туннеля |
| Deep diagnostic | Несколько RTT samples, jitter, loss, download throughput | Ручная диагностика и сбор подробных данных |
| Автопереключение | Сопоставимые свежие результаты и независимое подтверждение причины | Переключать только при доказанной деградации текущего сервера |

## 3. Обязательные атрибуты результата измерения

Каждый результат, который может участвовать в сравнении, должен иметь или однозначно наследовать:

- полный ключ профиля (не отображаемое имя и не только host/port);
- сетевой bucket: Wi-Fi / cellular / other;
- поколение/идентификатор сети или scan generation;
- время измерения;
- метод и endpoint набора проб;
- число успешных и общее число samples;
- latency, а при наличии — jitter, loss и throughput;
- признак свежести и признак успешного реального traffic validation.

Результаты из разных сетевых bucket, разных поколений сети или разных методов не сравниваются напрямую. Переход Wi-Fi ↔ cellular аннулирует пригодность старых результатов для нового выбора, даже если профиль тот же.

## 4. Правила preflight и выбора сервера

- Preflight выполняется только при остановленном VPN/core, как сейчас требует `DeepProbeEngine`.
- Профиль считается доступным только по принятому правилу успешных samples; единичный ответ не должен автоматически означать надёжность.
- Для первоначального подключения допустим быстрый выбор по median RTT среди успешно проверенных профилей текущей сети.
- Если нет свежего preflight для текущей сети, нельзя выдавать старые результаты за текущие. Нужно выполнить проверку или явно использовать безопасный fallback, не заявляя, что сервер проверен.
- Кэш результата должен включать полный ключ профиля, network bucket, scan generation и время. Текущий предел повторного использования connection scan — 90 секунд — сохраняется до отдельного обоснования изменения.
- Сканирование не должно выполняться параллельно с активным core, пока probe engine требует эксклюзивный `CorePortLease`.

## 5. Правила активного health-check

- Проверка через `127.0.0.1:10809` характеризует текущий VPN-маршрут. Она не является измерением отдельного сервера-кандидата.
- Успешный HTTP 204/2xx/3xx — подтверждение доступности контрольного endpoint через туннель, а не гарантия общей скорости или доступности всех сайтов.
- Один timeout не должен приводить к переключению. Сохраняются текущие подтверждения деградации, direct-vs-VPN сравнение, warmup, cooldown и лимит переключений.
- Если VPN отключён или ядро переходит между состояниями, результат должен быть fail-closed и не учитываться как валидное измерение сервера.
- Jitter вычисляется только из последовательных успешных samples одного активного туннеля и одной сетевой эпохи. После смены сети/профиля окно сбрасывается.

## 6. Контракт скоринга

- Все сравниваемые кандидаты должны иметь общий набор метрик и быть измерены в одном preflight batch на одной сети.
- Если throughput измерен только для части кандидатов, нельзя присваивать остальным нулевую скорость и сравнивать итоговые composite scores. Либо скорость измеряется для всех сравниваемых кандидатов, либо вес скорости исключается с перенормировкой оставшихся весов.
- Нельзя смешивать DeepProbe composite score, ScoringEngine score и latency-only ServerScanner score в одном ранжированном списке.
- Успешность истории должна быть привязана как минимум к полному ключу профиля и сетевому bucket. История на Wi-Fi не должна автоматически определять рейтинг того же профиля на мобильной сети.
- Нормализация метрик должна быть ограниченной, устойчивой к выбросам и одинаковой для всех кандидатов одного batch. Score без метаданных batch/network/method не пригоден для автоматического решения.
- Текущий порог преимущества 25%, warmup 90 секунд, cooldown 4 минуты и лимит 3 переключения за 15 минут сохраняются до появления доказательств, что их нужно менять.

## 7. Безопасный путь автоматического переключения

Пока нет активного механизма сопоставимого измерения альтернативных профилей во время работы основного core:

1. активный health-check выявляет подозрение на деградацию текущего туннеля;
2. отдельная проверка direct path определяет, не деградировала ли вся сеть;
3. альтернативы берутся только из последнего успешного preflight текущего network bucket и с допустимым возрастом;
4. если список устарел, пуст или относится к другой сети — не переключаться наугад; запускать предусмотренный recovery/reconnect path и получать свежие результаты при безопасно остановленном core;
5. после подключения TrafficValidator подтверждает фактический трафик; неудача учитывается как hard failure для точного профиля и текущего network bucket.

## 8. URLTest / резервные outbounds

В `AutoSwitcherConfig` объявлены `urlTestStandbyCount`, `urlTestInterval`, `urlTestToleranceMs` и `urlTestProbeUrl`, но статический поиск не обнаружил использования этих параметров в production-коде. Текущий `SingboxConfigBuilder.buildVpn()` создаёт TUN и локальный mixed inbound, но не создаёт `urltest` group и не добавляет standby outbounds.

Нельзя просто добавить urltest-группу: сначала требуется определить, как она будет соблюдать выбранный provider scope, ручной выбор, правила маршрутизации, отображение фактически выбранного outbound, blacklist, историю ошибок и семантику текущего сервера. Это отдельное архитектурное решение, а не безопасный однострочный фикс.

## 9. Подтверждённые несоответствия текущего кода

- `HomeViewModel` вызывает `rankInBackground()` после Connected, но `AutoSwitcher.rankInBackground()` прекращает работу, когда VPN core активен. Поэтому этот вызов не выполняет сравнительное ранжирование после обычного подключения.
- Если background ranking допустим к запуску, он передаёт в `ScoringEngine.computeScore()` только latency results; вес throughput 25% тогда получает нулевой вклад.
- `ScoringEngine.rankAll()` тестирует throughput только у top-5 latency-кандидатов, но затем сравнивает composite score всех кандидатов. Непроверенные по throughput профили получают speed=0, поэтому этот метод нельзя использовать для честного полного ранжирования без изменения контракта.
- `ServerScanner` строит собственную latency-only оценку и сортировку, а `DeepProbeEngine.run()` использует отдельную формулу 40/30/20/10. Эти scores не взаимозаменяемы.
- `ScoringEngine` сохранял историю по ключу профиля без network bucket, хотя blacklist и scan cache уже учитывают тип сети. Исправление начато в Draft PR #186; оно ещё не прошло CI.
- `ServerScanner.restoreCachedResults()` при отсутствии свежего scan cache создаёт `ScoredServer(latencyMs=1, successRate=0.75)` на основании факта успешного подключения в течение последних 7 дней. Значение 1 ms не является измерением RTT. Такой объект должен отображаться как «ранее работал / текущая проверка отсутствует», а не как сервер с ping 1 ms; его нельзя использовать как свежий preflight-кандидат. Исправление начато в Draft PR #187: latency=`Long.MAX_VALUE`, score=0, исторический success hint сохранён.
- Параметры URLTest объявлены, но фактическая urltest group в генераторе VPN-конфигурации отсутствует.

## 10. Порядок реализации

1. Ввести единый типизированный объект измерения с network identity, timestamp, method, sample counts и metric availability.
2. Добавить network-scoped history для ScoringEngine без миграции/потери существующей истории: старую историю считать legacy/neutral, а не приписывать новой сети.
3. Исправить скоринг частично измеренных throughput-кандидатов: отсутствие измерения — это unknown, не ноль.
4. Привести preflight и ручной DeepProbe к явному общему формату метрик, не смешивая их назначения.
5. Определить политику свежести и использовать её в recovery selection.
6. Только после этого отдельно спроектировать URLTest/standby outbounds либо безопасный stop-probe-reconnect механизм.
7. Проверки — через существующий CI; ручные тесты и устройство не заявлять без фактического выполнения.

## 11. Ограничения

Этот документ фиксирует контракт и статические наблюдения, но не утверждает, что runtime поведение проверено. Ручные тесты не запускались. Основной VPN-код не менялся в рамках P2.2.
